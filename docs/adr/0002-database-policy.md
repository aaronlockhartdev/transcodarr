# ADR-0002: Database policy before 1.0

Status: proposed. Human owner: Aaron; stamped `accepted (date)` at the merge that lands it.

## Context

transcodarr stores two kinds of data with different value: configuration and user intent (library
paths, watched/rating state, job rules), which cannot be recovered; and scan-derived cache, which
can be regenerated by re-scanning. The product is pre-1.0, so the schema will change destructively.
SQL is verified at compile time via sqlx's offline cache (`SQLX_OFFLINE=true`, committed `.sqlx/`),
which needs no live database.

## Decision

### SQLite + sqlx 0.9

Plain SQL migrations in `migrations/`, applied by `sqlx::migrate!()`.

### The schema is not frozen before 1.0

Destructive migrations are allowed and do not require
permission. What is banned: compat shims, `IF NOT EXISTS` inside migrations, dual-write columns,
and back-fill-and-drop dances that pretend the schema is stable. Left unstated, the two silent
failures are an agent stalling for permission on a migration, or shipping a dual-write column to
avoid destroying data.

### Two-tier data rule

Derived cache is disposable. User intent must survive a migration, and a
*test* is what proves it (see below). Prose cannot.

### The migration-intent gate

A test seeds a fixture database with **non-empty** user-intent rows,
snapshots per-column row counts and non-null counts, runs the migration set, and asserts they
survive. Empty-database tests cannot catch this class of bug. A hand-written table rebuild is
`CREATE TABLE new … INSERT INTO new SELECT … FROM old; DROP TABLE old`, and if the new
`CREATE TABLE` omits `rating`, a fresh empty database moves zero rows and nothing fails. Every
other gate stays green.

### Backup before migrate

The binary copies the live database to a per-worktree `backups/`
directory (retention keyed to the worktree) before migrating. `backups/` and `target/dev.db` are
gitignored, because untracked-but-present database files get committed by a reflexive `git add -A`
and deleted by a reflexive `git clean -fdx`.

### Three things never happen

Tests do not run against a real database. Library code does not
bulk-delete user intent; SQLite has no `TRUNCATE` statement, verified 2026-11-24 with
`sqlite3 :memory:`, which returns `near "TRUNCATE": syntax error`. Nobody edits an applied
migration, which the checksum path cannot catch in CI (see Rejected alternatives); the guard there
is a `git diff` check on `migrations/**`.

### Mechanical details belong in the file they govern

`build.rs` prints `cargo:rerun-if-changed=migrations` and `.gitattributes` pins `*.sql text
eol=lf`; each belongs as one comment inside that file once it exists. A *missing* line is the
silent failure, and the only reader who can cause it is standing on it. `migrations/` is
single-writer (ADR-0001). The `sqlx prepare` note lives in the `justfile`: migrations are not the
only path into the schema, and every agent writing SQL needs the same view.

## Rejected alternatives

|alternative|why rejected|
|---|---|
|`redb` (key/value)|every `SELECT … ORDER BY … LIMIT/GROUP BY` becomes hand-written scanning with hand-maintained indexes; no `sqlite3` CLI to inspect state by hand|
|`refinery`|its own README lists sqlx as *not* a supported driver; an adapter for a feature already owned by sqlx|
|diesel / sea-orm migrations|drags in an ORM the project did not ask for|
|"never destroy data before 1.0"|produces exactly the shims and dual-write columns we ban, and asks the human permission at every migration|
|banning permission-seeking outright (earlier draft)|reviewed and removed: it excluded the human from the one decision that can destroy their library, and was unfalsifiable anyway|
|trusting sqlx checksums to catch migration edits|structurally unreachable in CI: the checksum path only fires against a database with migration history, and tests use fresh temporary databases|

## Unenforced

- **Write the destructive migration; no compat shims.** Promised: grep the migration diff for
  `IF NOT EXISTS` and for columns added without being dropped. No `migrations/`, no `build.rs`, and
  `check.sh` greps for neither, so nothing tells a shim from a migration.
- **No bulk-deleting user intent; fresh temporary databases in tests.** Promised: a migration-intent test
  and a DSN assertion. `apps/server/tests/` holds the serving test only; the schema PR owes both.
- Post-apply migration edits, `build.rs` `rerun-if-changed`, `*.sql eol=lf` and "no `*.db` tracked" have no
  code. `check.sh` matches none of them; the only defence on `*.db` is `.gitignore:11`.
